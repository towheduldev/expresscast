# ExpressCast latency and performance roadmap

Source review of commit `34dc416`. Priorities reflect the code paths and failure modes visible in the repository. Actual latency, power use, and codec behavior still need measurements on physical phones and TVs.

| Priority | Work | Primary measure |
| --- | --- | --- |
| P0 | [Instrument the pipeline](#1-measurement), [coordinate startup](#2-stream-startup-and-lifecycle), and fix blocking and recovery on the [sender](#3-phone-capture-and-encoding), [network](#4-udp-video-and-loss-recovery), [TV](#5-tv-decoding-and-display), and [audio](#6-audio) paths. | First frame, video latency p95/p99, time frozen, audio underruns |
| P1 | Tune capture and codecs, reduce allocations, and add [network and thermal feedback](#7-network-and-device-adaptation). | Sustained frame cadence, queue age, allocation rate, dropped frames, power |
| P2 | Run [targeted experiments](#8-conditional-experiments) against the optimized H.264 and PCM baseline. | Improvement on the device and network that motivated the experiment |

## Current pipeline

```text
Phone screen -> MediaProjection / VirtualDisplay -> optional EGL crop
             -> H.264 encoder -> UDP fragments -> TV reassembly -> decoder
             -> SurfaceView -> display compositor / panel

Phone playback audio -> AudioRecord -> UDP PCM -> TV AudioTrack -> audio sink

TCP control -> pairing, stream start/stop, ping/pong, and keyframe requests
```

- The default is **1280×720 at a target of 60 fps and 6 Mb/s**, with 16:9 crop, audio and the stats overlay enabled. The default 16:9 selection takes the EGL path even when the captured content already has that aspect ratio. Native mode connects the virtual display straight to the encoder surface. The architecture notes still list 12 Mb/s in some places. [CastSettings.kt](../phone/src/main/java/com/expresscast/phone/settings/CastSettings.kt#L29) · [VideoStreamConfig.kt](../shared/src/main/kotlin/com/expresscast/shared/VideoStreamConfig.kt#L35) · [ScreenCaptureService.kt](../phone/src/main/java/com/expresscast/phone/capture/ScreenCaptureService.kt#L202) · [Architecture notes](architecture.md#6-codec-capability--fallback-strategy)
- Video v1 uses a 22-byte header and a 1,400-byte UDP datagram ceiling, leaving 1,378 bytes for each fragment. At 6 Mb/s and 60 fps, the mean encoded frame is about 12.5 kB, or about ten datagrams for a frame of that size. IDRs can be substantially larger. Audio sends 5 ms of 48 kHz 16-bit stereo PCM per full datagram, about 200 datagrams/s and 1.56 Mb/s including its 16-byte application header. IP, UDP, Wi-Fi overhead and retransmissions add to those rates. [NetworkConfig.kt](../shared/src/main/kotlin/com/expresscast/shared/NetworkConfig.kt#L19) · [VideoPacketHeader.kt](../shared/src/main/kotlin/com/expresscast/shared/VideoPacketHeader.kt#L69) · [AudioCaptureSender.kt](../phone/src/main/java/com/expresscast/phone/audio/AudioCaptureSender.kt#L150) · [AudioPacketHeader.kt](../shared/src/main/kotlin/com/expresscast/shared/AudioPacketHeader.kt#L43)

## 1. Measurement

**P0. Measure delays at each boundary.** Record sampled monotonic timestamps and join events by stream generation and frame ID. The sender can also use the encoder PTS to correlate capture and encode events once it has checked the timestamp source. Keep aggregation local and report histograms or trace slices rather than logging each packet.

| Stage | Record |
| --- | --- |
| Source and capture | Source cadence, captured content size, time from a test visual update to capture when observable, crop processing time, `eglSwapBuffers` duration, duplicate or skipped timestamps |
| Encode and send | Encoder output available, codec buffer released, sender queue age and depth, first and last UDP send, bytes and fragment count, IDR size and keyframe request to encoder output |
| Receive and decode | First and last fragment arrival, AU completion, loss or deadline reason, decoder input queued, decoder output ready and released, time spent awaiting input buffers |
| Display and audio | Surface render timestamp, frames released and presented where observable, panel presentation measured externally, audio samples captured/written/presented, buffered audio duration, underruns, drift and A/V skew |
| Session and resources | Discovery and pairing time separately from Start → first visible frame, loss → first good frame, reconnect and format changes, allocation/GC, CPU/GPU contention, memory high-water mark, thermal status and power |

**P0. Correct the overlay.** The TV label displays TCP ping/pong RTT and counts frames released to the output surface. Label these values **control RTT** and **submitted fps** until presentation data is available. Use a monotonic clock for RTT and FPS windows and show zero or a stale indicator when output stops. The phone also labels control RTT as latency. [TV overlay](../tv/src/main/java/com/expresscast/tv/MainActivity.kt#L203) · [TV RTT](../tv/src/main/java/com/expresscast/tv/network/TvControlClient.kt#L175) · [TV frame counter](../tv/src/main/java/com/expresscast/tv/codec/HardwareH264Decoder.kt#L164) · [Phone RTT](../phone/src/main/java/com/expresscast/phone/MainActivity.kt#L256)

Use `MediaCodec.OnFrameRenderedListener` for sampled surface timing and use the timestamp in the callback. Delivery can be delayed or batched. Capture Perfetto traces for thread scheduling, app markers, Binder, GC, and available graphics or buffer queue tracks. Perfetto documents a `SurfaceView` coverage limit for FrameTimeline, so use it for app/compositor context and corroborate video timing with codec samples and external measurement. [Android frame-render callback](https://developer.android.com/reference/android/media/MediaCodec.OnFrameRenderedListener) · [Perfetto FrameTimeline](https://perfetto.dev/docs/data-sources/frametimeline)

**P0. Establish a hardware baseline.** Record both screens together with a high-speed camera and a source that flashes a frame counter. At 240 fps, samples are about 4.17 ms apart. Use repeated transitions and a consistent location on each panel to account for scanout. For button-to-TV latency, film an input-linked LED or equivalent input marker and the TV. For audio, record a repeatable click/flash pattern and check onset, skew, and drift. In-app cross-device estimates require a four-timestamp monotonic clock exchange and an offset uncertainty estimate. TCP RTT/2 alone is an unreliable one-way video estimate on asymmetric paths.

**P0. Compare repeatable runs.** Use the same scene, profile, HDMI mode, device pair, and network for each before/after comparison. Capture p50/p95/p99 for steady-state delay and stage queue age. Also report first frame, freeze duration, delivered cadence, and drops by reason, so dropping late frames cannot make the latency statistics look better while playback gets worse. At 60 fps, one frame interval is 16.67 ms. Use that scale when evaluating each queue and include repeated cold starts and a 20–30 minute thermal run.

## 3. Phone capture and encoding

- **P0 · Release codec output before sending.** `HardwareH264Encoder` copies every AU into a new array, calls its listener, then releases the codec buffer. The listener packetizes, sends and sometimes sleeps on the same thread. Copy into a bounded pool of owned AU buffers, release the codec buffer in `finally`, and enqueue the owned buffer to a dedicated sender. Start with capacity for one or two pending AUs and impose an age/byte limit as well. Return the lease on send, drop, or shutdown. Under sustained overload, shed before encoding where possible. If an encoded reference AU must be dropped, reestablish a valid chain with a fresh IDR and codec config. [Encoder drain](../phone/src/main/java/com/expresscast/phone/codec/HardwareH264Encoder.kt#L135) · [Capture callback](../phone/src/main/java/com/expresscast/phone/capture/ScreenCaptureService.kt#L174) · [UDP send loop](../phone/src/main/java/com/expresscast/phone/network/UdpVideoSender.kt#L33)
- **P1 · Make direct surface capture the fast path.** Bypass EGL when the source and output have matching aspect ratios and the requested crop has no effect. Prototype TV-side scaling or clipping for mismatched ratios so the phone can keep the native surface path. Compare the trade-off for wide phones. A 20:9 image at 720 pixels tall has about 25% more pixels than 1280×720 at the same height. Extra encoder, network and TV work may outweigh savings on the phone. Keep the GPU crop path for cases where it wins or is needed for output framing. [ScreenCaptureService.kt](../phone/src/main/java/com/expresscast/phone/capture/ScreenCaptureService.kt#L202)
- **P1 · Cut work in the EGL crop path.** Cache attribute/uniform locations and static state per GL context. Trace `updateTexImage` and `eglSwapBuffers`, and coalesce redundant draw work when callbacks build up. Test using the latest texture timestamp to skip duplicate draws. Use a fixed-size GPU buffer or viewport sized for the useful crop and test whether the full-screen quad can safely skip the clear. Keep the transform and presentation timestamp, and report shader or EGL errors once with a controlled fallback. [CropSurfaceProcessor.kt](../phone/src/main/java/com/expresscast/phone/capture/CropSurfaceProcessor.kt#L185) · [Android SurfaceTexture](https://developer.android.com/reference/android/graphics/SurfaceTexture)
- **P1 · Track capture dimensions and bound the real capture rate.** The sizing and crop are set once from activity/resource display metrics. Use appropriate window metrics initially and the API 34+ `onCapturedContentResize` callback for rotation or single-app capture size changes. Resize and swap the surface on the existing virtual display as needed under Android 14+ consent rules. Test `KEY_MAX_FPS_TO_ENCODER` for surface input on API 29+ and measure actual AU cadence. In crop mode, skip excess frames before the GL draw when it is safe to do so. `KEY_FRAME_RATE` is an encoder hint, so check that 30 fps mode actually saves phone work. [Capture sizing](../phone/src/main/java/com/expresscast/phone/settings/CastSettings.kt#L37) · [Android projection resize](https://developer.android.com/reference/android/media/projection/MediaProjection.Callback#onCapturedContentResize(int,%20int)) · [Android 14 capture lifecycle](https://developer.android.com/about/versions/14/behavior-changes-14#media-projection) · [Encoder FPS limit](https://developer.android.com/reference/android/media/MediaFormat#KEY_MAX_FPS_TO_ENCODER)
- **P1 · Select and configure codecs by measured capability.** Check hardware status, surface input, size/alignment/rate and bitrate limits, AVC profile/level, available performance points, and the TV's constraints. Treat advertised rates as candidates and confirm by configure/start and a short soak with the game running. Retry with a fresh codec instance or a lower supported mode if initialization fails. Derive fallbacks from the requested aspect ratio and budget. The current fallback can jump to 1280×720 at 8 Mb/s for a smaller or lower-bitrate request, and returns an unchecked candidate when the size/rate checks fail. [Encoder selection](../phone/src/main/java/com/expresscast/phone/codec/HardwareH264Encoder.kt#L182) · [Android codec capabilities and performance points](https://developer.android.com/media/optimize/performance/codec)
- **P1 · Use the right latency controls.** The encoder currently sets `KEY_LOW_LATENCY`, which Android documents for decoding. Keep zero B-frames and try the optional encoder `KEY_LATENCY` in frames. Read back its actual value from the output format. A/B the existing operating-rate request of at least 120 fps against a rate matched to the negotiated cadence and against omitting the hint. Compare encoder delay, sustained phone game fps and thermals. Compare supported AVC profiles and rate-control modes at equivalent visual quality. Record peak IDR bytes and delivered bitrate, and count encoder drops if testing CBR with frame skipping. Keep H.264 hardware and surface I/O as the baseline. ## 4. UDP video and loss recovery

- **P0 · Make loss state independent of request throttling.** Reassembly currently reports a loss only alongside a later completed AU. The TV's callback for both decoder invalidation and requesting an IDR is gated by a 250 ms wall-clock cooldown. Signal an irrecoverable gap as soon as it is known. Use a monotonic expiry timer so an incomplete AU can expire even when the socket is idle. Enter a waiting-for-sync state immediately if the reference chain may have broken. Coalesce IDR requests per session, apply a monotonic cooldown to requests alone, and retry on a bounded deadline while awaiting sync. Carry internal queue drops into the same recovery logic. [Reassembly result](../shared/src/main/kotlin/com/expresscast/shared/VideoTransport.kt#L154) · [TV request cooldown](../tv/src/main/java/com/expresscast/tv/network/UdpVideoReceiver.kt#L103) · [TV loss callback](../tv/src/main/java/com/expresscast/tv/MainActivity.kt#L170)
- **P0 · Recover with a complete decoder start point.** The phone resends SPS/PPS as a separately numbered UDP AU before an IDR. Because of packet loss or reordering, the TV can see one without the other. Retain valid codec config for the current format/generation and wait until config and a suitable IDR are usable. Mark recovery only after input was accepted, then measure success at the first good decoded/presented frame. Consider a reliable config update on format change or an in-band SPS/PPS+IDR AU once the framing is negotiated. Test `KEY_PREPEND_HEADER_TO_SYNC_FRAMES` on supporting encoders with a configure fallback and verify the actual bitstream. [Current SPS/PPS sender](../phone/src/main/java/com/expresscast/phone/capture/ScreenCaptureService.kt#L174) · [Current TV input state](../tv/src/main/java/com/expresscast/tv/codec/HardwareH264Decoder.kt#L77) · [Android sync-frame headers](https://developer.android.com/reference/android/media/MediaFormat#KEY_PREPEND_HEADER_TO_SYNC_FRAMES)
- **P1 · Packetize in place and pool reassembly storage.** Replace the production sender's list of per-fragment byte arrays and packets with a reusable datagram, fixed header writes, and one fragment copied per send. Preserve the existing frame format and packetizer unit-test entry point while introducing a streaming API. The receiver currently allocates per fragment and copies all fragments into a second array at completion. The current packetizer uses a 1,378-byte stride for non-final fragments. Validate the expected lengths before writing to offsets in a pooled frame buffer and track received slots with a bitmap. Handle valid variable-length fragments through a bounded fallback if they remain supported. Carry the actual AU length and buffer lease to the decoder worker. Cap retained memory even after oversized IDRs. [Packetizer](../shared/src/main/kotlin/com/expresscast/shared/VideoTransport.kt#L8) · [Reassembly copies](../shared/src/main/kotlin/com/expresscast/shared/VideoTransport.kt#L100) · [UDP sender allocations](../phone/src/main/java/com/expresscast/phone/network/UdpVideoSender.kt#L33)
- **P1 · Bound reordering by a deadline.** The current reassembler abandons an older partial AU on the first packet of a newer AU, even if the older one would finish momentarily. Compare that mode against a tightly bounded policy that retains at most one additional AU for a short, measured reorder window. On a clean LAN, complete frames can still leave immediately in order. Expire incomplete frames by age and cap fragments, total bytes and metadata changes before allocation. Use unsigned 32-bit serial arithmetic for ordering/gap detection, including across rollover. Bind ingress to the paired peer and session generation so old datagrams cannot disrupt a new stream. A connected UDP socket needs a known sender port, so negotiate it or validate address and session with explicit filtering. [Reassembly state](../shared/src/main/kotlin/com/expresscast/shared/VideoTransport.kt#L79) · [Current wrap check](../shared/src/main/kotlin/com/expresscast/shared/VideoTransport.kt#L176)
- **P1 · Tune burst pacing with real link feedback.** The sender requests a 150 µs pause after every six fragments of a large frame. Benchmark it against no pacing and a small byte-based pacer with frame deadlines. Record actual sleep duration and compare IDR completion, loss, and tail latency. Fit bursts into the available link budget while leaving room for audio. Read back the actual kernel buffer sizes, then tune the requested 512 KiB send and 1 MiB receive buffers to absorb legitimate bursts without masking prolonged backlog. App queue age and socket drain measurements should drive the trade-off. [Send buffer and pacing](../phone/src/main/java/com/expresscast/phone/network/UdpVideoSender.kt#L19) · [Receive buffer](../tv/src/main/java/com/expresscast/tv/network/UdpVideoReceiver.kt#L57) · [RFC 8085 UDP burst mitigation](https://www.rfc-editor.org/rfc/rfc8085.html#section-3.1.6)
- **P1 · Tune recovery overhead on the control lane.** Keep TCP with `TCP_NODELAY` for reliable control. Use one ordered writer per session so keyframe requests and stream events avoid a new thread per action. Dispatch requests to the owning codec worker and coalesce duplicate requests while one sync is pending. Measure request → encoder output → first valid render. Compare the default 2-second keyframe interval with shorter settings on lossy links and longer settings on clean links. A shorter interval limits worst-case recovery when a request or IDR fails and adds bitrate bursts. [TV keyframe requests](../tv/src/main/java/com/expresscast/tv/network/TvControlClient.kt#L81) · [Phone forwarding](../phone/src/main/java/com/expresscast/phone/capture/ScreenCaptureService.kt#L387) · [Periodic IDR setting](../shared/src/main/kotlin/com/expresscast/shared/VideoStreamConfig.kt#L35)
- **P2 · Negotiate the datagram size only where useful.** Keep 1,400 bytes as the starting point for normal LANs. Test a smaller ceiling on constrained IPv6 paths, VPNs or other links where fragmentation or drops correlate with size. Test a larger ceiling only with confirmed path headroom and measure packet rate versus loss. Make the size part of the transport contract before changing reassembly stride. [Datagram ceiling](../shared/src/main/kotlin/com/expresscast/shared/NetworkConfig.kt#L19) · [RFC 8899 Datagram PLPMTUD](https://www.rfc-editor.org/rfc/rfc8899.html)

## 5. TV decoding and display

- **P0 · Keep socket reads independent from decoder availability.** The UDP receive callback runs `submitFrame`, which can wait up to 10 ms for an input buffer. Its Boolean result is ignored, and the decoder sets its keyframe state before input succeeds. Feed complete AUs through a small age-bounded queue to a dedicated codec worker. Return an explicit outcome for accepted, waiting for config/sync, backpressure, or codec failure. A missing decoder slot should carry over only while the AU is within its deadline. If the decoder misses a required reference, reenter recovery. [TV receive callback](../tv/src/main/java/com/expresscast/tv/MainActivity.kt#L170) · [Decoder submit path](../tv/src/main/java/com/expresscast/tv/codec/HardwareH264Decoder.kt#L77)
- **P0 · Serialize decoder setup, input, flush and teardown.** Own codec calls and state on a codec worker. Compare a synchronous worker with `MediaCodec.Callback` on a dedicated handler. The current 10 ms output dequeue is a maximum wait for an available buffer, so shortening it alone may just add wakeups. For non-adaptive decoders, flush and restart at a valid sync boundary on a discontinuity. In async mode, call `start()` after `flush()` and discard callbacks for invalidated buffers. Reapply CSD when needed, especially after an early flush. Recreate on format changes unless adaptive playback is supported and configured correctly. Ensure UI updates and surface replacement use the current session, since the current `AndroidView` factory captures the initial configuration. [Decoder drain and lifecycle](../tv/src/main/java/com/expresscast/tv/codec/HardwareH264Decoder.kt#L129) · [Surface factory](../tv/src/main/java/com/expresscast/tv/MainActivity.kt#L157) · [Android MediaCodec lifecycle](https://developer.android.com/reference/android/media/MediaCodec)

## 6. Audio

- **P0 · Decouple audio reads, network and playback where they block.** The TV writes to `AudioTrack` in blocking mode on the UDP receive thread, and the phone sends UDP on the capture thread. Give playback a small, time-bounded PCM ring with one track owner. It can use short or nonblocking writes, retaining the unwritten suffix only while timely. Split phone capture and sending if send timing shows audio reads being delayed. Reuse datagrams, buffers and header parsers. Handle short reads/writes, negative error codes, and stop or restart cleanly so a failed `AudioRecord.read` cannot spin. Reject partial PCM sample frames and track skipped sequences. [Phone audio loop](../phone/src/main/java/com/expresscast/phone/audio/AudioCaptureSender.kt#L114) · [TV audio loop](../tv/src/main/java/com/expresscast/tv/audio/UdpAudioReceiver.kt#L61) · [Android AudioTrack](https://developer.android.com/reference/android/media/AudioTrack)
- **P1 · Tune buffering in milliseconds on each output route.** The phone requests at least 7,680 bytes of capture capacity, equivalent to 40 ms of stereo PCM. The TV requests at least 3,840 bytes of track capacity, equivalent to 20 ms. These figures describe requested capacity. Use capture timestamps, audio frames written versus presented, and underruns to measure occupancy and delay. Keep `PERFORMANCE_MODE_LOW_LATENCY`, check the actual mode and output route, and test a smaller effective buffer with `setBufferSizeInFrames`. On API 31+, test a bounded start threshold. Use the smallest stable values for the target speakers, HDMI or soundbar, and measure Bluetooth separately. [Capture buffer](../phone/src/main/java/com/expresscast/phone/audio/AudioCaptureSender.kt#L50) · [Playback buffer](../tv/src/main/java/com/expresscast/tv/audio/UdpAudioReceiver.kt#L97) · [Android AudioTrack buffer sizing](https://developer.android.com/reference/android/media/AudioTrack#setBufferSizeInFrames(int))
- **P1 · Add audio timestamps, drift correction and loss handling.** The audio header has a sequence number and format, with no sample position or media timestamp. In a negotiated revision, send the first sample position per packet and an anchor tied to the same sender timeline as video. Use `AudioRecord.getTimestamp` and `AudioTrack.getTimestamp` where available. With a bounded jitter budget, reorder timely packets, conceal gaps with short silence or a crossfade, and discard expired audio. Track drift from sample position and buffer occupancy. If needed, use small resampling or playout corrections and resync on route/format changes. Keep audio correction bounded so it cannot steadily delay video. - **P1 · Fit PCM packet size and format to the operating mode.** Use 5 ms stereo PCM as the latency baseline. Test smaller chunks only when packet and wake-up costs are acceptable. A full 10 ms stereo PCM chunk is 1,920 bytes before headers, so a single such datagram exceeds the current ceiling. Evaluate a negotiated mono option for congested links or users who accept it. Align sample rates with the effective audio route where possible, and rebuild the track only when a real format/route change requires it. ## 8. Conditional experiments

Run each experiment only when its trigger appears in a trace or on the target device. Feature-gate it and compare with the simplest working configuration on clean and degraded links.

| Experiment | Trigger and evaluation |
| --- | --- |
| **Deadline-aware retransmission** | Isolated lost fragments cause frequent IDRs, and the measured RTT plus decode margin fits inside the AU's remaining deadline. Keep a byte- and age-bounded packet cache. NACK only repairable fragments, deprioritize retransmits behind fresh media, and fall back to IDR recovery when repair would arrive late. [RFC 4588 RTP retransmission design](https://www.rfc-editor.org/rfc/rfc4588) |
| **Forward error correction** | Repair RTT misses deadlines even though most loss is sparse. Try small parity groups or extra protection for config and IDRs first. Include parity bytes in the congestion budget. Test random and burst loss, added waiting time and battery impact. [RFC 8627 RTP forward error correction](https://www.rfc-editor.org/rfc/rfc8627) |
| **Intra refresh, temporal layers or slice-aware delivery** | Large IDR bursts or reference-chain recovery still dominate. Compare supported encoder intra refresh or temporal layering with shorter GOPs. Only discard enhancement pictures when dependencies are known. On decoders advertising partial-frame input, test feeding contiguous partial data early only if traces show meaningful reassembly delay. Verify loss recovery and fallback across vendors. [Android codec features](https://developer.android.com/reference/android/media/MediaCodecInfo.CodecCapabilities) · [AVC NAL packetization model](https://www.rfc-editor.org/rfc/rfc6184) |
| **HEVC or AV1 hardware mode** | H.264 quality is insufficient within the sustainable link budget. Require hardware encoding and decoding and measure first frame, bitrates at matched quality, encode/decode p95, IDR size and sustained thermals. Keep H.264 as the common profile. [Android codec capability queries](https://developer.android.com/media/optimize/performance/codec) |
| **Opus or native low-latency playback** | PCM bandwidth or Android audio output delay is material. Test negotiated Opus with short frames and include codec lookahead, decode time and loss concealment. Separately test AAudio/Oboe only if profiling points to the output implementation. Keep PCM over a known-good route for comparison. [Opus specification](https://www.rfc-editor.org/rfc/rfc6716) · [Android low-latency audio](https://developer.android.com/games/sdk/oboe/low-latency-audio) |
| **Native or batched UDP** | Allocation work is already bounded and traces still show per-datagram socket CPU or wakeups dominate. Prototype a small JNI `sendmmsg`/`recvmmsg` path on supported targets. Flush partial batches promptly, preserve per-packet length and deadlines, and compare latency, CPU and maintenance cost with the JVM implementation. |
| **RTP/RTCP, QUIC DATAGRAM or a direct link** | A hard requirement emerges for interoperability, integrated packet feedback or resilience on the existing LAN. Measure RTP/RTCP or an unreliable QUIC datagram transport at the same latency and quality targets. Independently test a direct link only if supported hardware and an unreliable AP justify extra setup complexity. Keep UDP media and reliable control as the benchmark. [RFC 6184 H.264 RTP](https://www.rfc-editor.org/rfc/rfc6184) · [RFC 9221 QUIC DATAGRAM](https://www.rfc-editor.org/rfc/rfc9221) |
| **Codec and app warmup** | Start → first frame misses its target after readiness changes. A/B cached capabilities, warm decoder setup after pairing with a timeout, and a persistent encoder input surface where startup traces justify reusing it. Verify lifecycle correctness and memory impact. Try a Baseline Profile for measured Android startup or app-code hotspots and verify in a release-like build. [MediaCodec persistent input surface](https://developer.android.com/reference/android/media/MediaCodec#createPersistentInputSurface()) · [Android Baseline Profiles](https://developer.android.com/topic/performance/baselineprofiles/overview) |
